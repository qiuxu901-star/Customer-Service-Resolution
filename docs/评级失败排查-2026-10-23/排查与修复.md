# 评级失败排查与修复

## 排查范围

读取本地 `solve-eval-app/data/db.json` 的历史评级输入、原始返回和错误，不修改正式数据。历史共247条评级、55条失败（包含旧协议及重复重试，不代表独立工单失败率）；最近一次运行19条，成功9条、失败10条。

用户列出的第4项与第6项为同一类错误。逐项结论如下。

| 用户报错 | 证据与原因 | 本次调整 |
| --- | --- | --- |
| 责任结论自身存在问题时须标明影响责任结论 | 历史35次。模型已将问题定位到 `ai_analysis_conclusion`，却将影响标记填false；返回中的理由常为“判责方向未变”，或只说明建议笼统、核查范围不清。协议中的“影响责任结论”容易被理解为改变判责方向，实际校验包含对该字段使用和理解的影响。 | 在字段契约、系统说明、提交前检查和纠错反馈中统一语义：默认结论自身存在问题时标true，不代表关键错误或必须L0；影响描述保留实际程度。详情问题仍独立判断，不能仅因核对引用包含结论而认定结论出错。 |
| 已确认具体帮助时不能定为L1 | 本地历史未找到这一报错原始记录，因此不声称已复现用户该次返回。触发条件明确：`grade=L1`且具体帮助列表非空。公共标准的L1定义要求尚无可确认具体帮助；原系统没有将该定义直接写成输出字段联动自检。 | 明确L1的具体帮助为空、实质帮助未确认；若确有成果，按核心错误及任务完成度重新判断，不机械提档或删除真实成果。新增模拟回归复现并纠正这一矛盾，补验L1与实质帮助依据的一致性。 |
| 模型未返回有效JSON | 历史5次，原始字符串均无法通过JSON.parse；既有字段名后的冒号错误，也有引号或嵌套结构错误。请求虽已有json_object模式，供应商返回仍可能损坏；原流程一次解析失败即终止。 | 保留严格JSON解析，强调字符串转义；语法损坏反馈模型重新返回完整JSON，最多一次。HTTP、网络及输出截断不自动重发，不在程序内拼补或猜测内容。 |
| 具体帮助证据编号不存在或不是本条有效材料（第4、6项） | 历史2次实际均是具体帮助对象遗漏了 `evidence_refs` 属性，虽然正文依据中写了E编号。原报错将字段缺失与非法编号归为同一句，容易误判为引用越界。 | 明确每项成果四个必填字段，正文编号不能替代引用数组；逐单提供允许的证据编号及AI输出编号集合，错误反馈区分字段缺失与非法值，直接定位到 helpful_contributions[i].evidence_refs，并重复提供每项必填字段及结构示例；校验仍拒绝跨单、虚构或source代替segment编号。 |
| 规则引用不存在或类型不正确 | 历史3次；其中2次明确将实际 `P001` 等编号缩写成 `P1` 等，另一次涉及不正确的引用类型。规则正文自己的章节号和引用索引存在混淆空间。 | 提供本单规则编号集合，明确逐字复制、不缩写、不引用正文章节号，不适用时空数组；错误引用反馈模型纠正，不由程序推测映射。 |

## 实现

评级协议升级为 `resolution-llm/v5.10`。新正式评级、评估员试评及方案试用默认均使用带校验反馈的表现评级请求；业务Skill诊断、分类请求维持原调用路径。

首次有效报告只调用一次。JSON损坏或报告校验失败时，沿用同一工单、规则和模型，追加原始返回与错误反馈，最多再调用一次；二次仍失败按失败保存，不生成伪U，不自动改变等级、填补证据或删除问题。纠错请求也受输入字符和1MB限制。两次返回、错误、总用量、耗时与可计算费用留档，未知用量不计作零。方案确认页同时说明通常一次、含纠错最多两次模型调用。

允许编号集合只加入表现评级输入，不改变诊断输入的规则引用约束。业务公共标准的已发布版本、正式历史报告及人工复核均未改写。
